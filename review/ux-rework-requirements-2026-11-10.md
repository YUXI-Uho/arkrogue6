# 前端体验改造需求计划书（待评审）

日期：2026-11-10　状态：需求草案，P0 主链路已开始实施

## 1. 目标与边界

产品的核心任务是：选择干员和藏品，快速看出谁的哪些数值变了、为什么变，以及条件未满足时该改什么。现有数据、计算、仓储模块已能支撑这条链路；本轮重点改展示和操作，不重写计算规则。

目标：

1. 常用任务在一个工作区内完成，减少编队、藏品、战斗状态、汇总之间的反复切页。
2. 先显示结论与变化，再按需展开来源、条件和公式；让未生效或无法计算的项目同样可见。
3. 桌面与手机都能完成完整流程，而非手机只勉强能打开。
4. 保留当前存档、分享链接、离线使用和可追溯的计算口径。

本计划不包含新藏品解析、技能伤害规则扩充、截图识别、服务端账号或云同步。若体验改造发现数值错误，单独列缺陷并修复，不借 UI 改动悄悄改变计算口径。

## 2. 当前基线与待验证问题

代码现状：桌面采用藏品库与工作区双列；工作区有“编队、汇总、战斗状态、技能”四个页签。藏品瓦片为了密度隐藏效果正文，详情需弹窗；编队卡同时放名字、职业、位置、详情、删除、面板编辑及结果；伤害估算在汇总页，影响结果的条件输入在另一页。窄屏改为上下堆叠，藏品库限制为 40vh。

这些设计可能产生的体验问题，需要在真实浏览器确认：

- 选藏品后，需要跨页找最终变化；遇到条件不满足，又要跳到战斗状态页寻找对应输入。
- 密集藏品瓦片难以在选择时判断效果、适用对象和档位差别。
- 编队卡的常用操作与高级编辑混在一起；12 个槽位在窄屏上可能难以辨认和点击。
- 汇总页同时承担面板对照、伤害估算、属性汇总，主结论被次级内容稀释。
- 现有冒烟测试使用 DOM 桩，不能证明实际布局、触控面积、焦点流和滚动体验。旧评审明确记载了这项验证缺口。

上面是基于代码的诊断假设，不当作已完成的用户访谈结论。实施前先在 1366×768、768×1024、390×844 的真实浏览器中记录截图和任务路径，并覆盖空状态、1 人 2 藏品、12 人满编及大量条件未满足四种状态。

## 3. 信息架构与页面方案

### 3.1 主工作区

将“组建配置 → 看到结果”作为默认页面，而不是把结果放在另一个主页签。

- 桌面：藏品选择、编队、结果摘要同时可见；只让需要浏览的长列表滚动，避免多层嵌套滚动。结果区保留当前干员、关键数值变化和未生效提示。
- 手机：以“藏品 / 编队 / 结果”三个明确入口切换同一配置，并在底部保持可见的简短结果与已选数量。切换不清空搜索、选择和滚动位置。
- “战斗状态”改为从相关结果或条件提示打开的抽屉/面板；仍保留查看全部条件的入口。
- “技能查询”保留独立工具入口；选择干员/技能后能返回原工作区，并明确哪些倍率是从文案提取、哪些必须手填。

先做低保真线框和一套可点击原型，评审通过后再写代码。上述布局是推荐方向，最终桌面列宽和手机导航以原型实测为准。

### 3.2 信息优先级

每个结果按四层呈现：**最终值与变化 → 影响来源 → 条件与作用范围 → 公式/原始数据**。默认层不展示全部 11 项面板、所有修正明细和长篇说明；需要时能在原位置展开。所有数值同时标明基准值与最终值，百分比、固定值和“未计入面板”分开说明。

## 5. 视觉与可用性规范

- 保留深色主题的基础识别，但重做字号、间距、层级和状态色：正文以 14–16px 为主；选中、未满足、未量化不能只靠颜色区分。最终色板与组件在原型阶段确认。
- 卡片只承载一个主要动作；危险操作不与主要动作同权重。关键按钮在手机上有足够触控面积，不依赖悬停才能发现。
- 统一搜索框、筛选器、数字输入、抽屉、弹窗、提示和空状态的行为；输入错误就地反馈，保留用户已输入内容。
- 键盘可完成搜索、选中、调档、切换干员、打开/关闭详情；焦点返回触发位置。支持 200% 缩放、减少动态效果偏好和可见焦点。
- 不为“游戏风格”引入无法合法取得的角色立绘或外部字体。若需要官方图标，先确认来源、许可和离线打包方案。

## 6. 实施顺序与评审关口

1. **基线审计**：真实浏览器截图、三条任务路径录屏/点击数、窄屏与满编检查；形成问题清单，确认优先级。
2. **原型评审**：桌面和手机线框、主任务可点击原型、空状态/结果状态视觉稿。此关口确认导航结构与风格，不进入大规模重写。
3. **P0 主链路**：工作区、藏品、编队、结果先落地；保留旧存档兼容；完成后进行第一轮真实浏览器验收。
4. **P1 完整功能**：战斗状态、伤害、技能、存档/分享接入新结构；逐模块补端到端交互测试。
5. **P2 打磨与发布**：帮助文案、可访问性、性能、回归与灰度发布；上线后验证旧存档恢复及线上关键路径。

每一关口都给出截图或可运行预览、已知问题和验收结果，让评审基于实际页面决定是否继续。不会把“代码已模块化”当成体验完成的证据。

## 7. 统一验收标准

- 主任务：加入 1 名干员、选择 2 件藏品、调整其中一件的档位、读出最终攻击力与来源，在桌面工作区内完成，期间无需切主页面。
- 条件任务：从一项未生效结果直达对应状态输入，修改后返回可见的结果；保持用户原有配置。
- 布局：在 1366×768、768×1024、390×844 下无横向溢出、遮挡关键操作或不可达的弹窗；12 人满编和长名称也需检查。
- 状态：旧本地存档、备份恢复、预设、分享链接、离线访问都通过回归；刷新、切视图和返回后保持选择与编辑状态。
- 测试：保留现有引擎/数据/API/DOM 冒烟测试；增加真实浏览器的主任务、条件任务、导入导出、键盘与手机触控用例。视觉截图和交互录像纳入评审，不再只靠 DOM 桩判定完成。

## 8. 请在原型前确定的产品选择

1. 主要使用场景：电脑上长时间配队，还是手机边玩边查？两端都做，但主场景决定首屏信息密度。
2. 视觉方向：延续当前深色工具风格，还是向《明日方舟》的工业信息界面靠近？后者需明确素材边界。
3. 首页默认视角：以“编队干员结果”为中心，还是以“藏品清单”为中心？本草案推荐前者。

这些是评审项，不影响先做基线审计；未决定前不锁定最终视觉稿。
