## 四、五个「重点怀疑」的逐个回答

1. **`MANUAL_STACK_COND` 会不会漏掉「官方给了 perStack 但文案没写每层」的藏品？**
   **不会。** 我按「任一阶段出现 `perLayer` 或 `cond.type ∈ {perStack, capLayer}`」扫全库，与「实际渲染出层数框」的集合求差：**差集为空**。原因是 `needsStack` 的第一项就是 `hasStackFlag`，而所有 perStack 藏品都带 `stack` 标记；反过来 196 这种没有 `stack` 标记的，靠 `MANUAL_STACK_COND.perStack` 兜住（实测有框、max=40）。
   真正的漏在**反方向**：白名单管不住 `hasStackFlag` 的误触发（7 个空转框，见 N4）。

2. **152 的 `cap` 夹倍数会不会影响别的 `perProfession` 藏品？**
   **不会。** 全库 `perProfession` 只有 152 一条；`capFactor` 在没有 `cap` 时原样返回。我另外验了没有 cap 的 `perResource` / `perAlly`：106（allyCount=4 → factor 4）、192（ingots=20 → 4）、199（parts=20 → 20）都没有被夹。

3. **「整组一起丢」会不会误伤正常的多属性加成？**
   **当前数据不会。** `'攻击力和防御力各+30%'` → 2 条、`'攻击力+30%，防御力+30%'` → 2 条、`'所有我方单位仅阻挡1名敌人时，攻击力和防御力+50%'` → 2 条。全库扫描确认守卫只丢了 086 那一条 `block:1`。
   **但根判定仍偏宽**：`'生命值低于50%时，生命+50%'` 会被整组吞掉（见 N5），只是现在没有这种文案。

4. **空控制条修好后，有没有误伤「已选中但确实该有控制条」的卡片？**
   **没有。** 逐件选中扫描：有控制条 27 张（13 张阶段下拉 + 14 张层数框，无重叠），其中子节点为空 **0** 张；152 单独确认 `relic-controls === null`。

5. **「另有 N 项」会不会在切换战斗状态时不刷新？**
   **不会。** `getSummary()` 的缓存键是 `modsKey + JSON.stringify(ctx)`（`js/app.js:280`），ctx 一变键就变。实测 144：time=30 → 无提示；time=90 → 「另有 2 项」；回到 30 → 提示消失。152 侧同样：术师 0 → 「另有 1 项」，术师 3 → 「+36%」。

## 六、做得好的地方

1. **152 的修法是把「语义」放回数据，而不是把「层数框」藏起来**：`detectCond` 本来就能产出 `perProfession`，这次没有在 UI 上做特判、也没有加 id 白名单，而是让「最多叠加8层」在上游被识别为**上限**（`effects.js:321-326`），下游 `capFactor` 只夹倍数。所以同一套代码同时解释得通「术师 3 名 = 36%」和「术师 12 名 = 96%」。
2. **空名是两端一起兜的，而不是只堵一边**：`onblur` 管「用户编出来的状态」，`normalizeEntry` 管「已经落盘的坏档」，中间还留了「输入过程中允许临时为空，不打断打字」。这比单纯在 `oninput` 里改值体验好得多。
3. **守卫的「整组丢/留」是想清楚了边界才写的**：注释里明确写了「只按数值相等逐条丢会把『攻击力和生命+50%』吃掉一半」，并且特意只认汉字动词、不认 `+/-`（否则 086 会复发）。这种「先写清楚为什么不能更宽松」的注释，比代码本身有价值。
4. **`check_enums.py` 的修复是「让它能失败」而不是「让它更好看」**：剥注释、按赋值匹配、认 `forEach` 批量赋值，三步都指向同一个目标——删掉一行结算必须报错。我做了 4 组破坏实验才敢写「属实」。
5. **删文件之前先确认了依赖方向**：`relics_wiki.js` 删、`.json` 留，并且把「不再生成 .js」写进了 `parse_relics.py` 的注释。这是本轮唯一一次「删对了」的判断。

## 七、是否达到 demo 交付标准

### 结论：**可以交付**（demo / 内部工具标准）

理由：

1. **没有会丢数据或崩界面的问题**。三轮里最危险的两类（存档丢人、导入白屏）都已闭环，`deserialize` 对 16 组脏输入的降级路径还在。
2. **没有系统性的算错**。全库 251 件里，能被证明「算错数」的只剩 2 件（209、142），且都是**召唤物专属效果被当成全体**这一类边界，不是解析主干崩了。相比之下 round-1 的 086 是「每名干员都白送 100% 攻击」，量级完全不同。
3. **能力边界是可见的**。解析不了的进「特殊效果」卡，条件不满足的进「另有 N 项」，不可结算的进「未计入面板」——用户不会看到「什么都没发生还不知道为什么」。
4. **三条命令绿、离线可跑、加属性/加藏品都只动一处**，作为 demo 的工程底线是够的。

**但交付时必须带一份「已知问题」**，至少写清 209 和 142：这两件藏品会让主表的数字偏大/偏小，评审如果随手点中会被问住。如果还有半天时间，**只修 209 一件**（见下节第 1 条），交付风险就基本归零。

不建议因为这两条就压着不发：它们是历史遗留、单件、且修法明确，不构成架构问题。

## 九、如果继续迭代，最值得做的三件事

1. **修 209（最高性价比，半小时内）**：在 `parseRelic` 合并「官方 + 文案补充」时，如果文案项与我方/敌方**同名同值**的官方项冲突（`enemyAtk` vs `atk`、`|value|` 与 `pct` 都相等），就不要补；或者在 `effects.js` 的 `detectScope` 里给「猎犬/proto/召唤物/无人机」这类**非干员主体**加一条早退，返回 `{base:'summon'}` 而不是落进「全体我方」兜底。顺手把 142 一起救（它的 `hp/atk +20%` 也走同一条兜底）。**加一条断言：勾 209 后 `final.atk` 不变。**
2. **把「条件类型 → 需要什么控件」收敛成一份元数据**：在 `core/schema.js` 或 `effects.js` 导出 `COND_META = { perStack: {manual:true}, perProfession: {ctx:'profCounts'}, perResource:{ctx:'ingots|parts|value'}, … }`，让 `app.js` 的 `MANUAL_STACK_COND` 和 `engine.js` 的 `SCALE_COND_TYPES` 都从它派生。这样「加一种 cond 类型要改三处」变成改一处，也顺手消掉 `perLayer: 1` 死条目和 engine 少 `perResource` 的不一致。
3. **把「层数框有没有用」变成可测的**：给 14 个带框的藏品各写一条「stack 0 → 5 结果必须变化」的断言（我这次是临时脚本扫的）。现在这 7 个空转框之所以能活三轮，就是因为没有一条测试问过「这个框改了有没有效果」。同一批测试也能顺手覆盖 216 的「有 cond 但没有 ctx 驱动口」——凡是 `perResource(res:'value')` 就该在 `buildCtx` 里有对应键。

（低成本收尾：把 `tests/engine.test.js:282` 那条「生命值低于30%时最大生命+30% → 0 条」改成 `ok(...)` 加注释说明是已知限制，别把它当成正确行为钉死。）
